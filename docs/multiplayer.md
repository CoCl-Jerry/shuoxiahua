# 联机模式（v1.18 已上线）与实现记录

## v1.17 已经打好的地基

**规则引擎抽纯了。**`engineApply(action)` 是唯一能动牌局状态的地方：
动作进（`{t:'play'|'pass'|'call', seat, cards?, rank?}`），事件出
（`played / passed / burn / reveal / win`）。引擎不碰界面、声音、AI、
表情 —— 那些全在展示层听事件（`presentEvents`）。非法动作（错座位、
不是你的牌、张数超限、重复牌）一律抛错打回，这就是将来防作弊的第一道闸。

**状态可序列化。**`serializeGame() / loadGame(json)` 一对函数，
含协议版本号 `PROTO`。断线重连、旁观者入座、中途存档都靠它。

**规则快照。**每局开局把 SET 拷进 `ECFG`，一局之内规则不变 ——
联机时房主定规则，快照随发牌一起同步。

**AI 与人对称。**真人和 AI 现在都只产出动作对象，引擎不区分来源。
远程玩家就是第三种动作来源，主循环一行都不用改。

已验证：300 局模糊测试（1.5 万个动作），牌守恒、非法动作全拦、
序列化往返一致。

## v1.18 实现的方式

**主机权威制。**一台手机开局当主机：引擎只在主机跑，客机把动作发过去，
主机验证后把事件广播给所有人。天然防改牌（客机根本没有别人的手牌数据——
广播事件时按座位过滤，只发你看得见的信息）。

**传输选型（按省事排序）：**
1. **PeerJS（WebRTC）** —— 免费公共信令服务器，房主生成 4 位房号，
   其他人输号直连。无需自己架服务器，适合家里人对战。缺点：公共信令
   偶尔抽风，iOS Safari 后台会断。
2. **Firebase Realtime DB 免费档** —— 动作写进房间节点，各端监听。
   稳，但要注册个项目，密钥得进代码（免费档滥用风险可接受）。
3. 自己架 WebSocket —— 最稳，但违背"零服务器"的初衷，先不做。

**座位规则。**主机开房 → 选几个真人几个 AI → 空座位由主机跑本地 AI
补上（AI 逻辑已在，斗嘴照常）。断线的真人座位由 AI 代打，重连时
`loadGame` 快照接手。

**每步的协议消息**（草案）：
```json
→ 主机 {"proto":1,"t":"act","act":{"t":"play","seat":2,"cards":[17,30],"rank":6}}
← 广播 {"proto":1,"t":"ev","evs":[{"e":"played","seat":2,"rank":6,"n":2,"out":false}]}
← 入座 {"proto":1,"t":"sync","game":"<serializeGame() 按座位过滤后>"}
```
注意：广播 `played` 事件本来就不含具体牌面（只有张数和报的点数），
`reveal` 事件才亮牌 —— 跟线下打牌的信息面完全一致。

## 动手顺序建议

1. 先做「同屏传手机」模式（零网络：一台手机轮流传着打，引擎已支持多真人座位，只缺换座时的遮牌界面）—— 一天的活，还能当联机的 UI 彩排。
2. 再上 PeerJS 两台真机对战。
3. 稳定后加断线代打和重连。

## v1.18 实测记录

- 本地信令服务器 + 两个浏览器端到端：连接、入座、发牌同步、双端打完整局，
  胜负一致、每家手牌张数逐一吻合，重复十余轮。
- 客机只拿到自己的手牌和各家张数；`played` 事件天生不含牌面，
  `reveal` 才亮牌，收进别人手里的 `gained` 广播时替换为空数组。
- 兜底双保险：客机看门狗 5 秒自查"轮到我却没在等我"的悬空态；
  房主 90 秒无响应由 AI 代出一手；中途掉线的座位转为 AI 代打并全桌广播。
- 版本闸：客机 join 时带版本号，房主不一致直接拒绝，防止两端逻辑不同步。
